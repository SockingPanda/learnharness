# Interface internationalization

The shared web/desktop application interface supports `en` and `zh-CN`.
Settings → General → Interface language offers Follow system, 简体中文,
and English. The default is Follow system; unsupported language preferences
fall back to English. Chinese regional variants currently use Simplified
Chinese. AI response language and speech recognition settings remain
independent.

## Ownership and persistence

- `src/core/i18n.ts` contains pure language negotiation, cookie parsing,
  interpolation and the assembled message catalog. It is exported through
  the existing browser-safe core barrel.
- `src/core/i18n/*.ts` groups translations by UI area. English source messages
  are the lookup keys and the English fallback. The dictionaries contain
  application copy only.
- `components/i18n.tsx` provides the current locale and translator to the
  entire interface, including portaled settings and dialogs. Changing the
  language rerenders existing components without resetting their state.
- `app/layout.tsx` resolves the `lh-locale` cookie and request
  `Accept-Language`, then passes the same locale to the HTML element and
  provider for hydration. Existing routes remain unchanged.

The `lh-locale` cookie stores `system`, `en`, or `zh-CN` with a one-year
lifetime and root path. It belongs to the current browser/Electron profile,
not the server's shared settings record. Browser language changes update
Follow system mode. Other open windows receive a `storage` invalidation
and reread the cookie; regaining focus also resynchronizes. The storage
signal contains no second persisted language preference.

There is no process-global mutable locale, so simultaneous server requests
can render different languages. Standalone component renders without a
provider default to English.

## Authoring copy

Use `const { t } = useI18n()` inside a client component. Add the English
message and Chinese translation to the dictionary for that UI area:

```tsx
const { t } = useI18n();
return <button aria-label={t("Close settings")}>{t("Close")}</button>;
```

Translate complete messages with named placeholders, including count
variants, rather than concatenating translated fragments:

```tsx
t(count === 1 ? "{count} node" : "{count} nodes", { count });
```

Non-React presentation helpers can accept an optional `Translator` with
`createTranslator("en")` as the default. Translation must happen at render
time for labels in constant maps. Keep IDs, protocol values, keyboard
bindings and test IDs stable across locales. Technical provider/model names
and file paths stay verbatim. Use the supplied `locale` for locale-dependent
formatting when needed.

User messages, notes, session titles, model replies, graph propositions,
quiz content, code, exports and provider diagnostics retain their source
text. Pass only known interface labels to `t`; do not translate arbitrary
content just because it matches a catalog key. The first version covers
the shared application interface; native operating-system menus and
provider-hosted sign-in pages remain under their respective hosts.

## Verification and extension

`tests/i18n.test.tsx` checks negotiation, corrupt cookies, fallback behavior,
placeholder parity, static translation call coverage and Chinese SSR.
`tests/i18n-interaction.test.tsx` exercises live switching, preference
persistence, system-language changes, cross-window invalidation, hydration
and retention of an unsent draft. The existing English render and behavior
tests remain part of the normal test suite.

To add a language, extend `UiLocale`, preference validation and negotiation,
provide a complete catalog, expose its native name in `LanguageSetting`,
and extend the negotiation/catalog tests. No conversation or graph migration
is required.
